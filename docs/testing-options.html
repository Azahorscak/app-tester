Decision brief · app-tester

The Upgrade Guard

Thirty-odd third-party apps in one Kubernetes cluster, upgraded by engineers who can't be expected to know every edge case each vendor just changed. The pods go Ready; the search box quietly stopped working. Here is the tooling landscape for catching that in-cluster, on open source, without a platform bill — and with three pieces of the answer already sitting in the cluster.

01

The constraint that shapes every other choice

We don't own these applications. We can't add test hooks, we don't control the release notes, and the DOM and routes change without warning. That makes hand-written, selector-heavy test scripts the single most expensive thing we could build — every upstream release turns into test maintenance, and a suite that needs repair every Tuesday gets ignored by Thursday.

So weight the suite toward techniques whose per-app authoring cost is close to zero, and spend the scripting budget only on the two or three journeys per app that would actually page someone.

Technique Authoring cost per app What it catches that nothing else does
Visual diffing A list of URLs Layout breaks, vanished buttons, CSS regressions — the exact "UI elements broke" complaint, with no assertions written
Console & network assertions One shared fixture, reused everywhere JS exceptions, 4xx/5xx during page load, broken asset paths
Spec-driven API fuzzing Zero, if the app publishes OpenAPI Boundary values, type mismatches, constraint violations — edge cases nobody thought to write down
Spec diffing between versions Zero Breaking API changes, spotted before the upgrade is applied
Accessibility / DOM scans Zero Structural breakage: lost labels, orphaned landmarks, broken form associations
Scripted user journeys High — and re-paid at every upgrade Real multi-step workflow breakage. Irreplaceable, but ration it.

Where the tester plugs into the upgrade path

03

Placement: everything lands on the spot pool

Every pod in this system is ephemeral or disposable, so all of it belongs on the existing spot pool. Substitute the real label and taint key — the shape is identical everywhere: 

# The fragment. Goes into every pod spec this system creates.
nodeSelector:
  <spot-pool-label>: "true"        # karpenter.sh/capacity-type: spot
                                   # cloud.google.com/gke-spot: "true"
                                   # eks.amazonaws.com/capacityType: SPOT
tolerations:
  - key: "<spot-taint-key>"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
Component Path the fragment goes into
Playwright test Jobspec.template.spec
Argo CD PostSync hook Jobspec.template.spec — it is an ordinary Job
Nightly CronJobspec.jobTemplate.spec.template.spec
MinIO OperatorHelm operator.nodeSelector / operator.tolerations
MinIO Tenantspec.pools[].nodeSelector and spec.pools[].tolerations — separate from the operator's own
TestkubeChart values and the executor job template — executors spawn their own pods
Argo WorkflowsworkflowDefaults.spec in the controller ConfigMap, so every workflow inherits it
KuberhealthyChart values and each KuberhealthyCheck pod spec — checks run as their own pods

The gotcha worth internalising

An operator's own placement is not inherited by the pods it creates. Testkube executors, Kuberhealthy checks, k6 runners and MinIO Tenant pods are each spawned by a controller and each need the fragment configured separately. Miss one and it schedules onto the default pool — where it works perfectly, and quietly bills on-demand rates until someone reads an invoice.

Spot-specific hardening

Preemption is the price of the pool, and it arrives disguised as a test failure unless we handle it deliberately.

A reclaimed run is not a red result

Set restartPolicy: Never and backoffLimit: 2 so a preempted run retries rather than reporting a regression that never happened. Before treating a run as failed, check for a DisruptionTarget pod condition — that's node reclamation, not the app.

Never let preemption trip a gate

Critical in Stack C: a progressive-delivery controller sees a failed analysis webhook and rolls back. Report a verdict only from a run that actually reached completion. A rollback caused by a spot reclaim would destroy trust in the gate on day one.

Give scale-up room

A PostSync Job may sit Pending for a minute or two while a spot node is provisioned. Set activeDeadlineSeconds generously — 1800 suits a full suite — and don't alert on pending-under-five-minutes.

Spread, don't concentrate

Independent Jobs per app beat one Job with thirty steps: a single reclaimed node then costs one app's run instead of the entire sweep. Keep terminationGracePeriodSeconds short — there's nothing to drain.

The one thing on spot worth arguing about

The MinIO Tenant is the only stateful component here, and spot reclamation restarts its pods underneath it. That is a sound trade on one condition: the bucket must hold nothing irreplaceable.

  • Screenshot baselines live in git, beside the tests, approved by pull request. They are the source of truth and must never live only in the bucket.
  • MinIO holds only disposable output — HTML reports, traces, videos — under an ILM expiry rule. Thirty days is plenty and keeps it small.
  • Back the Tenant with network-attached PVs, not local disk, so a reclaimed node reattaches instead of losing the volume.

With those three in place, losing the Tenant costs you old report history and nothing else. If you'd rather not lose even that, pin only the Tenant to on-demand by dropping the fragment from spec.pools[] — that is the single line to change, and everything else stays on spot.

04

Layer one — what actually exercises the app

Browser & UI

PlaywrightApache-2.0

The default recommendation

One tool covers UI and API assertions. Built-in screenshot comparison (toHaveScreenshot()), a recorder (codegen) that turns clicking around into a test file, and a trace viewer that gives a DOM-level replay of any failure — which is exactly what lets a junior engineer see what broke without reproducing it. Official container images; auto-waiting kills most of the classic flake class.

Robot Framework + BrowserApache-2.0

If juniors will author, not just run

Playwright underneath, plain-language keyword syntax on top, human-readable reports by default. Worth it specifically because the people applying upgrades are the people who should be able to read and extend these tests.

CypressMIT core

Good DX, awkward economics

Excellent authoring experience, but parallelisation and the dashboard sit in the paid Cypress Cloud. sorry-cypress is the self-hosted OSS replacement.

Check sorry-cypress maintenance activity before betting the setup on it.

Selenium GridApache-2.0

Only for inherited suites

If existing Selenium tests come with an app, Grid runs fine in-cluster. Don't start here: heavier to operate and more flake-prone than Playwright.

API

SchemathesisMIT

The direct answer to "we don't know when edge cases are hit"

Property-based testing generated from an OpenAPI or GraphQL schema. It invents boundary values, type mismatches and constraint violations on its own, then flags responses that violate the app's own spec. Zero per-endpoint maintenance, and it routinely finds real bugs on a first run.

Needs the app to publish a spec. Where one exists, this is the highest finds-per-hour tool on the page.

HurlApache-2.0

Cheapest useful smoke checks

Plain-text request/assert files, a single static binary, a tiny container. Best cost-to-value in the whole API column, and simple enough that anyone can read and edit one without a tutorial.

oasdiffopen source

Warning before the upgrade lands

Diffs the old and new OpenAPI specs and classifies breaking changes. Run it against the incoming image pre-sync. The cheapest early warning available, and it costs one short-lived pod.

k6AGPL-3.0

Performance regressions a functional suite can't see

Load testing, but check() also does functional assertions, and k6-operator runs it as a CRD with Prometheus output. Catches the upgrade that still works but got four times slower.

BrunoOSS core

Postman replacement with a GUI

Git-native API client with a CLI runner, for when someone wants to author against a visual client. Some features sit behind a paid edition.

axe-coreMPL-2.0

Structure checks disguised as a11y rules

Via @axe-core/playwright. Accessibility rules double as a structural integrity check — a disappeared label or a broken landmark shows up here for free.

Visual regression

Playwright screenshotsbuilt in

One less moving part

Baselines live in git next to the tests, diffs land in the same HTML report. Unless there's a reason to decouple visual testing from the functional suite, start here.

BackstopJSMIT

Standalone visual regression

Its own config format and HTML diff report, Playwright- or Puppeteer-backed. Choose it if visual coverage should span apps that have no functional suite at all.

Lost Pixel, the usual OSS Percy/Chromatic alternative, was archived in April 2026 — don't start a new deployment there.

05

Layer two — what schedules and collects the runs

Job / CronJobalready in the cluster

The floor, and genuinely viable

One image with the suite, a CronJob for the nightly baseline, kubectl create job --from=cronjob/… for ad-hoc runs, and ttlSecondsAfterFinished for cleanup. Zero added infrastructure, zero always-on cost. Its only weakness is ergonomics: no UI, results live wherever you push them.

TestkubeMIT + community lic.

Kubernetes-native test orchestration

Tests become CRDs; it runs Playwright, Cypress, k6, Postman, JMeter and curl as pods, and can trigger suites off Kubernetes events — such as a Deployment image change, which maps exactly onto our upgrade workflow. The agent is self-hosted and standalone.

The agent is the open-source piece; the polished dashboard and multi-environment features belong to the commercial Control Plane. Verify the current OSS boundary against their docs before committing.

Argo WorkflowsApache-2.0 · CNCF

Flexibility without adopting a testing product

A general DAG engine: fan out thirty apps × three suites in parallel, retry, pass artifacts, and get a decent UI. Pairs with Argo Events for triggering. The right answer if we'd rather own a pipeline than a platform.

KuberhealthyCNCF

Continuous probes, not regression suites

An operator that runs synthetic checks as pods on a schedule and exports pass/fail to Prometheus. Different shape from the rest — "can I still log in, does search answer" every few minutes. Complementary, and cheap.

Chainsaw / kuttlopen source

Assertions about the cluster, not the app

Declarative YAML checks on Kubernetes resources after an upgrade: did the ConfigMap keys survive, did the CRD version migrate. Not app testing, but it catches a real class of upgrade breakage at almost no cost.

TektonApache-2.0

Only if already running

Kubernetes-native pipelines. Perfectly capable here, but not worth adopting solely for this if nothing else in the cluster uses it.

Layer three — the trigger that removes human memory from the loop

This is the layer that actually addresses the stated problem. The engineer applying the upgrade should not have to remember to run anything.

Trigger Fires when What happens on failure Cost to adopt
Argo CD PostSync hook ← the pick Every successful sync — i.e. every upgrade Sync is marked failed. Does not roll back on its own — pair with a SyncFail hook or a notification. An annotation on a Job. Argo CD is already running.
Argo Rollouts / Flagger New version gets a slice of traffic; suite runs as an analysis gate Controller reverts automatically. The bad upgrade undoes itself. A controller, plus mesh or ingress traffic splitting. Prefer Argo Rollouts — shares tooling with the Argo CD already in place.
Testkube event trigger A watched Kubernetes event, no GitOps required Recorded as a failed execution; alert out A CRD, if Testkube is already in
CronJob backstop Nightly, regardless of deploys Alert only Effectively nothing
On-demand run An engineer wants a before/after on one app They read the report A documented one-liner or a UI button

What the PostSync hook looks like, concretely

metadata:
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded

HookSucceeded is deliberate: passing runs clean themselves up, while a failed run's Job and pod stay put so a junior engineer can read the logs without re-running anything.

Wire Argo CD Notifications to the on-sync-failed trigger and post the MinIO report link straight to chat — that's alerting without standing up Alertmanager for it. And with an ApplicationSet, the same hook template generates across the whole fleet, so onboarding an app becomes a list entry rather than a new manifest.

Layer four — where results go

MinIO Tenantoperator already in place

Cheapest reporting that anyone will actually open

One Tenant, one bucket, laid out s3://app-tests/<app>/<run-id>/. The Job's final step is an mc cp --recursive; the resulting URL goes into the Argo CD notification, so the alert is the link. The trace viewer is the payoff: a failure becomes something you scrub through, not something you reproduce.

A 30-day ILM expiry rule keeps it from ever becoming a line item. Baselines don't live here — they live in git.

Prometheus + GrafanaApache-2.0

Almost certainly already running

Pass/fail and duration as time series, alerts via Alertmanager to Slack or Mattermost. Kuberhealthy and k6 emit metrics natively; everything else can push to a Pushgateway.

Allure ReportApache-2.0

History and flakiness trends

With allure-docker-service, cross-framework reports that answer the question that matters on a failure: is this new? Worth adding once there are more than a handful of suites.

ReportPortalApache-2.0

Powerful, and the one real budget risk here

Excellent aggregation and failure clustering, but it wants Postgres, RabbitMQ and OpenSearch running permanently.

This can cost more to host than the tests it reports on. Skip until the suite count clearly justifies it.

Layer five — optional, for selector churn

Because we don't own these apps, a test that breaks because the vendor renamed a CSS class is a false positive — and false positives are how a suite loses its audience.

Playwright codegenbuilt in

Reach for this first

Re-record a broken flow in a minute rather than debugging selectors. The non-AI answer, and usually the sufficient one.

Midscene.jsMIT

Steps in natural language, elements located by vision

"Click the login button" survives a redesign that would break a CSS selector. Supports self-hosted open-weight vision models such as UI-TARS and Qwen-VL.

Self-hosting a vision model means GPU nodes, which would dwarf every other line in this budget. A hosted model API is cheap per call but isn't self-hosted.

LLM triage onlypragmatic middle

Keep the hot path deterministic

Tests stay ordinary code. On failure only, hand the diff and trace to a model to draft "likely a real regression" vs "likely a selector rename." A few calls per failed run costs cents and never touches a passing run.

08

Keeping the bill small

Browser pods are the expensive part: budget roughly 1 vCPU and 1.5–2 GB per concurrent Chromium instance, and cap worker count explicitly rather than letting Playwright scale to the node's core count.

The spot pool is already there, so most of this is paid for — see Placement above for the fragment and the preemption handling that makes it safe. The one thing worth confirming is that the pool actually scales to zero when idle; a spot pool holding a warm node costs money for nothing between runs.

Set ttlSecondsAfterFinished on every test Job and prune artifacts on a schedule; screenshot baselines and traces grow fast. Use the pre-built official runner images rather than installing browsers at pod start — it saves minutes and bandwidth on every single run. And resist always-on platforms until the suite count earns them.

09

What will bite

Screenshot flake
Font rendering, animations, timestamps and live data all produce diffs that aren't regressions. Generate baselines inside the same pinned container image that runs them, disable animations, freeze the clock, mask dynamic regions — and pin the browser version, because an unpinned bump invalidates every baseline at once.
Apps with no OpenAPI spec
Schemathesis and oasdiff are simply unavailable. Fall back to recorded-traffic replay: capture a HAR of a known-good session, replay it, assert on status codes and response shape.
State accumulation
These apps keep data between runs, so tests drift into failure for reasons that have nothing to do with the upgrade. Reset via the app's own API at suite start, or deploy a fresh ephemeral namespace per run and tear it down — the second is cleaner and, on scale-to-zero nodes, barely more expensive.
Credentials
Tests need real logins. Keep them in Kubernetes Secrets (External Secrets or Sealed Secrets under GitOps), never in the test repo, and never reuse a credential that exists anywhere outside this cluster.
Baseline approval
When a visual diff is an intended change, someone has to approve the new baseline. Make that a pull request, not a --update-snapshots run on someone's laptop, or the safety net quietly dissolves into a rubber stamp.
Loss of trust
A suite that cries wolf gets ignored, and then the upgrade problem is back with extra infrastructure attached. Quarantine flaky checks into a non-blocking lane rather than letting them fail the gate — and never gate on a suite that still flakes.
10

Recommendation

Build Stack A against three representative apps — one UI-heavy, one API-only, one that's both. With Argo CD, the spot pool and the MinIO operator already in hand, the genuinely new pieces are small: a Playwright image, a Job manifest, a Tenant, and one Kyverno policy.

Order of work for that first stack:

  1. Namespace app-testing, plus the Kyverno policy that pins everything in it to the spot pool.
  2. MinIO Tenant with a 30-day ILM expiry rule, credentials in a Secret.
  3. Playwright image with the suite; baselines committed to git, generated inside that same image.
  4. PostSync hook Job (hook-delete-policy: HookSucceeded) plus a nightly CronJob backstop.
  5. Argo CD Notifications on on-sync-failed, carrying the MinIO report link.
  6. Roll out across the fleet with an ApplicationSet.

Then add, in this order:

  1. Schemathesis for every app that publishes a spec. Highest ratio of edge cases found to effort spent, and it directly targets the "juniors don't know when edge cases are hit" problem.
  2. Testkube or Argo Workflows, once bare Jobs get awkward — adopted mainly for the self-service UI, not for the execution. Configure placement on their executor pod templates, not just the controller.
  3. Argo Rollouts auto-revert, once the suite is trusted enough to be a gate — preferred over Flagger since Argo CD is already here. Not before; a flaky gate is worse than no gate, and spot preemption must be provably distinguishable from a real failure first.
